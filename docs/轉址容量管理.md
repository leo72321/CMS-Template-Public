# Cloudflare Pages 301 轉址：容量、防呆與自動退役

所有 POST、PAGE 的正式 URL 照原本 SEO 架構產生；**不用建立空白網頁或 JavaScript 跳轉**。部署用的 `public/_redirects` 在建置時依設定重新計算，內容仍是 Cloudflare Pages 原生的 301 規則。

## 一、全站設定（site.config.json）

```json
{
  "redirectManagement": {
    "maxActive": 1950,
    "overflowAutoPrune": true,
    "agePrune": {
      "enabled": false,
      "days": 90
    }
  }
}
```

這是既有 `site.config.json` 的其中一個頂層欄位，**不要直接用這段 JSON 覆蓋整份站台設定**。

### 第一個防呆：容量與提醒

- 候選轉址總數首次達 **1,500、1,800、1,950** 條，分別通知一次。
- 超過 **1,950** 後，候選規則每增加一條便多一筆通知（例如 1951、1952……），同次大量新增會彙整在同一份 Actions 通知。
- 預設 **`maxActive: 1950`、`overflowAutoPrune: true`**。超過 1950 時**自動淘汰建立順序最舊的有效 301**，始終保留最多 1950 條部署規則；被淘汰的規則不再輸出。
- 如將 `overflowAutoPrune` 設為 `false`，超過 `maxActive` 時就**拒絕建置**，而不是部署超額轉址。
- `maxActive` 可設 1–2000，預設 1950 留下 50 條緩衝。提醒門檻仍以原始候選總數 1500／1800／1950 計算。

### 第二個防呆：建立日期清理（預設關閉）

- `agePrune.enabled` 預設 **false**：即使某條轉址已超過 90 天，也**絕對不會因為日期而刪除**。
- 改為 `true` 才會啟用；`agePrune.days` 預設 **90**，可自行修改。
- 判斷依據是 **`createdAt`（首次有紀錄的建立日期）**，不是「最後一次訪客請求」或「90 天沒人點擊」。
- 如果要實作真正的「連續 XX 天沒有人請求過才清除」，必須另接 Cloudflare 的請求資料來源。本專案**沒有假裝自己已掌握訪客存取紀錄**。

## 二、歷史紀錄不會因重新部署被洗掉

`content/redirect-ledger.json` 保存每一條轉址的：

- `createdAt`：第一次記錄該轉址的日期；
- `sequence`：同一天建立時，仍可固定判定哪一條先出現；
- `target`：目前或退役前的轉址目標；
- `retiredAt`、`retiredReason`：永久退役的日期與原因（`capacity` 或 `age`）；
- `alerts`：已提醒過的里程碑和 1950 以上候選總數高水位。

**目前舊資料原先沒有 timestamp**。首次遷移的既有轉址以 **2026-10-23** 做首次記錄基準，`sequence` 按既有 `url-lock.json` 的穩定順序排序；這不是原始歷史建立日期。

退役記錄保留在 JSON 作為 **tombstone**。建置時先排除這些舊路徑，不會因未來 POST 重新產生同一轉址，就讓已淘汰的規則復活。

`content/url-lock.json` 仍是文章正式網址及現行 301 的保護清單：一般意外刪除仍被阻擋，**只有已列在 tombstone 的自動退役規則**允許從公開 301 清單消失。正式文章的標準網址、分類頁、TAG 頁、Sitemap 均不因 301 淘汰而刪除。

## 三、GitHub 自動提醒與資料保存

`scripts/redirects.ts` 提供：

- `npm run redirects:sync`：同步歷史台帳和 `url-lock.json`，產生 `.reports/REDIRECT_MAINTENANCE.md`／`.json`；
- `npm run redirects:check`：檢查歷史台帳及網址鎖是否已同步，不修改資料。

`.github/workflows/轉址容量維護.yml` 負責在主要內容或站台設定推送到 main 時，自動執行 `redirects:sync`，再以 GitHub Actions 的內建 `GITHUB_TOKEN`（不用 Cloudflare Token）將新台帳**提交回 main**。有新容量提醒或新退役項目時，除了 Actions 摘要，也會嘗試建立 GitHub Issue；不用架設 Worker 或外部服務。

另有每日 CRON：**若日期清理沒有啟用，會在安裝依賴之前直接跳過**；只有設定 `agePrune.enabled: true` 才真正執行到期維護。

> 自動持久化仰賴 GitHub Actions 對儲存庫的 `contents:write` 權限，以及 main 分支允許機器人推送。若組織另設分支保護使推送失敗，Workflow 會顯示紅燈；程式建置仍會依容量上限輸出，但必須先修正寫入權限才能保證台帳長期累積。

## 四、測試與安全

轉址模組有測試涵蓋：1500／1800／1950 不重複提醒、1950 以後逐條新增提醒、超額淘汰先後次序、90 天日期開關、關閉自動淘汰時 fail-closed、退役規則不可復活。

後續若要恢復退役連結，需要先確認不撞正式網址，再**明確移除對應的 tombstone**，不能讓網頁或匯入流程偷偷恢復。
