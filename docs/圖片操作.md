# 圖片操作

給圖片路徑、文章 ID 與替代文字，工具會縮圖、上傳並填回文章。

## 第一次設定

先完成 [網站基本資料初始化](初始化精靈.md)；再從唯一的 **Actions → 圖床設定｜S3 一站式驗證與套用** 選供應商＋機房和 Bucket；有自訂 CDN 優先填寫，沒有才手動啟用 B2 原生公開網址。Run 會先測試 S3 上傳，再對 CDN 做一次匿名 HEAD 連結檢查（不下載檔案），才決定是否套用設定。詳見 [圖床設定操作](S3圖床設定.md)。

複製 `.env.example` 為本機 `.env`，填入金鑰：

| 本機變數 | 用途 |
| --- | --- |
| `S3_ACCESS_KEY_ID` | S3 金鑰 ID；B2 對應 Application Key ID |
| `S3_SECRET_ACCESS_KEY` | S3 私密金鑰；B2 對應 Application Key |

如果要在 GitHub 按鈕測試 B2／S3，則把同名金鑰放在 **私人倉庫**的 GitHub Actions Secrets，千萬不要填進表單或 JSON。請參考 [一站式圖床設定與連線驗收](初始化精靈.md)。

未經新版初始化的既有 B2 Native 網站仍可用 `B2_APPLICATION_KEY_ID`、`B2_APPLICATION_KEY`、`B2_BUCKET_ID`，不會被強制遷移。

**CDN URL（完整前綴，例如 `https://cdn.網域/file/桶名/`）必須把公開網址下的 `網域/...` 映射到 Bucket 內 `網域/...` 的同一物件**；單純填子網域不會自動設好 Origin 或公開讀取權限。

## 封面

先設定自己的網域，再執行：

```bash
npm run media:add -- --uid 範例新增文章 --file "D:/圖片/cover.png" --alt "文章與分類的關係" --cover
```

產生單尺寸 WebP（最大寬 1440，小圖不放大）；封面額外產生 1200 × 630 的分享圖片。成功後自動寫入 `cover` 的網址、替代文字、寬高與各尺寸。

## 內文

先在內文放唯一占位符：

```markdown
<!-- 圖片:流程圖 -->
```

再執行：

```bash
npm run media:add -- --uid 範例新增文章 --file "D:/圖片/流程.png" --alt "從寫作到發布的流程" --name 流程圖
```

成功後換成 Markdown 圖片，建置時補上寬高、自適應尺寸與延遲載入。封面可重跑覆換；內文重插時，先將原圖片換回占位符。

加 `--dry-run`（預覽模式）只列出處理結果與目標網址，不上傳、不改文章、不需金鑰。

## 上傳成功與連結檢查

圖片轉檔後交給 B2 Native 或 S3 上傳 API。**API 明確成功後，只對這次上傳的圖片網址發出一次 HTTP HEAD**，確認連結是 2xx，且回應標頭沒有顯示 HTML 假圖片或空檔案。不使用 GET 下載媒體內容，不計算下載後雜湊，也不對同一張圖連續重試。若 HEAD 回 404／403／405 或不正確的類型，就顯示錯誤並暫停更新文章，請檢查 CDN 設定。

B2 Native API 的 SHA-1 是該 API 上傳所需的原生校驗欄位，與重新下載檔案無關；媒體 manifest 仍保留現有 SHA-1、尺寸、時間等欄位，確保既有資料相容。S3 API 接收上傳成功回應後不額外 GET 檔案。內容雜湊仍可用於避免圖片同名與快取衝突。

**正常 CI 只驗證程式、內容與媒體索引，不連線下載或重新 HEAD 已上傳圖片。** 不排程每週巡檢，也不額外消耗 CDN 圖片流量。

需要手動查死圖時，才執行：

```bash
npm run media:verify              # 對目前使用中的遠端連結逐一 HEAD
npm run media:verify -- --batch-size 1000  # 手動分批 HEAD
```

上面不下載媒體內容；此處僅檢查 HTTP 可達性和已提供的回應類型，**不能保證檔案內部每個位元組都正確或圖片一定能成功解碼**。真正發現異常時再另外人工查看。

## 大型網站的媒體成本

- `content/media/manifest.json` 保留圖片尺寸、URL 和上傳收據，圖片本體仍在 B2／S3。
- 媒體索引使用 URL → 資料的 Map，避免每篇文章重複掃描整份媒體清單。
- 已有圖片平時不做遠端掃描、不另加週期性 GitHub Runner 成本。
- `npm run media:orphans` 只輸出未使用檔案候選清單，**不會自動刪除遠端圖片**。
- 既有 B2 Native 與新版 S3 仍共存；已經公開的圖片網址不會因為此驗證調整而改變。

## CPT 圖片路徑

新上傳圖片依 `網域/site|blog|CPT代碼/永久UID/檔案` 儲存，不與會改變的文章分類及 Slug 綁定。已存在的圖片路徑保持不動，操作詳見 [CPT 自訂內容](CPT自訂內容.md)。

## 附件上傳：PDF／ZIP／Office 及其他檔案

`media:add` 已同時支援一般附件，不必額外做圖床或手動填網址。**附件不經 Sharp、不轉檔、不產生縮圖；由 B2／S3 API 上傳成功，再對公開 URL HEAD 一次，不下載回來校驗。**

CPT 自動填入單一附件（需先在 `site.config.json` 把欄位定義成 `type: file`）：

```bash
npm run media:add -- --uid 20261023-k7m2q --file "./report.pdf" --field report
```

相簿則 `--field photos`（`type: gallery`）搭配圖片與 `--alt`，每次上傳會追加一張；單張 `image` 欄位則覆寫該欄位。非 CPT 的一般文章／Page 使用正文占位符：

```markdown
<!-- 檔案:guide -->
```

```bash
npm run media:add -- --uid 文章UID --file "./manual.zip" --name guide --label "使用手冊 ZIP"
```

自動插入可點擊的下載連結。增加 `--dry-run` 可先預覽目標物件 Key、CDN 網址和欄位，完全不修改內容、不需要金鑰。常見允許格式：PDF／ZIP／7Z／RAR／Word／Excel／PowerPoint／CSV／TXT／RTF／MP3／MP4／WebM；單檔最多 **100 MiB**，不允許 HTML／SVG／程式執行檔。

新附件與圖片共用 `content/media/manifest.json` 的上傳收據及孤兒報表；附件不會被錯誤要求圖片寬高，並且不會改動舊媒體 URL。

**目前設定的公開圖床只適合可以讓訪客下載的檔案，不能把車主個資、合約、機密文件丟到公開 B2 Bucket。** 私有附件若需要登入授權下載，要另外部署對應的權限驗證／短效連結服務；本功能不會自動公開原本的私桶。

## 不用本機 KEY：直接從 GitHub Actions 上傳附件

如果兩組 S3 KEY 已經放進 Repository secrets，可以直接用 **Actions → 媒體上傳｜圖片與 PDF／ZIP 附件 → Run workflow**，不必在本機重填 `.env`，也不必申請 GitHub Token。

| Actions 欄位 | 填法 |
| --- | --- |
| `uid` | CPT／Blog／Page 的永久 UID，例如 `20261023-k7m2q` |
| `source_url` | **優先建議**：可用 HTTP GET 直接下載的 HTTPS 檔案網址，例如你已有的 B2 公開下載連結（與 `source_path` 擇一） |
| `source_path` | 若來源在 Repo 內，填相對檔案路徑如 `media-inbox/report.pdf`（與 `source_url` 擇一） |
| `field` | CPT `file` 欄位如 `report`，相簿 `gallery` 如 `photos`；一般 Blog/Page 留白 |
| `name` | Blog/Page 正文占位符名稱，如 `guide`；用 `--field` 時可留空 |
| `label` | Blog/Page 的下載連結名稱；CPT 可留空 |
| `alt` | 上傳圖片必填替代文字；PDF／ZIP 等附件留空 |
| `cover` | 只有封面圖片選 true，附件維持 false |
| `dry_run` | 第一次預設 true，只預覽不寫入；確認無誤後改 false 再 Run |
| `runner` | GitHub Hosted 或現有 self-hosted Runner，與網站驗收相同的切換邏輯 |

**完整流程：** Actions 先下載指定來源至本次 Runner（有設定 100 MiB 檔案上限）；下一步才讀取 GitHub Secrets 呼叫 B2／S3 上傳、HEAD 檢查連結，成功後更新 Markdown／CPT 欄位和 `content/media/manifest.json`，執行 `docs:update`，由既有的 `GITHUB_TOKEN` 提交到 `main`。失敗或 `dry_run=true` 時不提交。資料來源必須已存在且 URL 允許直接存取，這個表單**不是電腦選檔上傳介面**，也不會幫你從私有本機路徑取得檔案。

**注意：** 直接把附件提交進 GitHub Repo 作為 `source_path` 會在 Git 歷史留下那份附件，即使日後刪掉也不會自動從歷史消失。大檔案建議用 HTTPS 來源，不要先丟進 Repo；敏感個資或內部文件不可丟進公開 B2 Bucket。
