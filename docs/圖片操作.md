# 圖片操作

給圖片路徑、文章 ID 與替代文字，工具會縮圖、上傳並填回文章。

## 第一次設定

請先使用 [中文網站初始化精靈](初始化精靈.md)，選擇 B2、R2、AWS S3 或其他相容儲存，並設定 S3 Endpoint（端點）、Region（區域）、Bucket（儲存桶）與 CDN 子網域。

複製 `.env.example` 為本機 `.env`，填入金鑰：

| 本機變數 | 用途 |
| --- | --- |
| `S3_ACCESS_KEY_ID` | S3 金鑰 ID；B2 對應 Application Key ID |
| `S3_SECRET_ACCESS_KEY` | S3 私密金鑰；B2 對應 Application Key |

如果要在 GitHub 按鈕測試 B2／S3，則把同名金鑰放在 **私人倉庫**的 GitHub Actions Secrets，千萬不要填進表單或 JSON。請參考 [圖床連線測試步驟](初始化精靈.md)。

未經新版初始化的既有 B2 Native 網站仍可用 `B2_APPLICATION_KEY_ID`、`B2_APPLICATION_KEY`、`B2_BUCKET_ID`，不會被強制遷移。

**CDN 必須把 `https://cdn.網域/網域/...` 真正映射到 Bucket 內 `網域/...` 的同一物件**；單純填子網域不會自動設好 Origin 或公開讀取權限。

## 封面

先設定自己的網域，再執行：

```bash
npm run media:add -- --uid 範例新增文章 --file "D:/圖片/cover.png" --alt "文章與分類的關係" --cover
```

產生最大寬度 480、960、1440 的 WebP，小圖不放大；另產生 1200 × 630 的分享圖片。成功後自動寫入 `cover` 的網址、替代文字、寬高與各尺寸。

## 內文

先在內文放唯一占位符：

```markdown
<!-- 圖片:流程圖 -->
```

再執行：

```bash
npm run media:add -- --uid 範例新增文章 --file "D:/圖片/流程.png" --alt "從寫作到發布的流程" --name 流程圖
```

成功後換成 Markdown 圖片，建置時補上寬高、自適應尺寸與延遲載入。封面可重跑覆換；內文重插時，先將原圖片換回占位符。

加 `--dry-run`（預覽模式）只列出處理結果與目標網址，不上傳、不改文章、不需金鑰。

## 上傳成功的定義

新版 S3 上傳會透過官方 AWS S3 SDK 寫入指定 Bucket，再從 CDN 下載並以 SHA-256 比對內容；全部成功才改文章及 `content/media/manifest.json`。舊 B2 Native 模式保留原有 B2 校驗程序。

若 S3／B2 上傳後 CDN 尚未可讀，文章保持原狀。修好後可重跑；失敗過程可能留下未引用物件或同名版本，工具不會擅自刪除。

檔名含內容雜湊。CDN 必須保留原始位元組，不可在同一路徑自動轉檔，否則校驗會失敗。

發布前執行 `npm run media:verify`。**一般 CI 只會遠端重新驗證本次新增加／修改的圖片**；已經有成功上傳收據的既有圖片只做本地索引查核，避免大量下載。完整與分批驗證請見下文。

固定素材也可放 `public/`，以 `/圖片.webp` 引用。Markdown 圖片仍需替代文字，建置時會讀本機尺寸。一般文章圖片建議走已設定的 S3 相容儲存服務。

## 大型網站的媒體成本控制（5,000 頁也適用）

**資料格式不變。** 內文圖片在 POST／PAGE 的 Markdown 只是 `![alt](https://cdn...)`；封面在 frontmatter 保留主圖、OG、各尺寸與 alt。真實圖片放 B2／S3；`content/media/manifest.json` 留驗證收據與尺寸，不把圖片二進位存進 GitHub。

- 媒體清單在 Astro 建置時使用檔案變更偵測＋**一次建立 URL → 資料的 Map**。不同文章重複使用同一張圖片，不會重新解析整份 JSON 或掃描所有檔案。
- B2／S3 的 **上傳階段仍會讀回完整 CDN 內容驗證**；上傳失敗不得改寫文章。
- 一般 GitHub CI 的 `npm run media:verify` 透過 Git 基準版本比較 `manifest.json`，**只下載本次新增加／更新的媒體**。既有收據的 SHA1、驗證時間及圖片尺寸仍全部做本地檢查，不重新下載數萬張。
- 手動完整驗證：`npm run media:verify -- --full`，會讀取全部被引用的遠端媒體，屬於較昂貴的操作。
- 分批巡檢：`npm run media:verify -- --batch-size 1000`，每次以固定週序號輪流選 1000 個。`Actions → 媒體 CDN 分批巡檢` 可手動選 Batch/Full；有實際媒體才會每週自動巡檢 1000 個。校驗失敗會使 Action 失敗。
- 孤兒媒體候選：`npm run media:orphans`，生成 `.reports/MEDIA_UNUSED.md` 與 `.json`；**僅提供人工確認清單，不會自動從 B2／S3 刪除**。

**重要界線：** 因 CDN 可能在上傳後遭修改、外部網址可能被其他系統引用，增量 CI 只能保證「提交時有有效上傳驗證收據、且新增／修改媒體有實際 CDN 校驗」。要確認所有既有圖片現在仍可讀，必須使用完整／分批巡檢。孤兒報表無法得知站外引用或歷史回滾所需檔案，因此不能直接批次刪除。

**大規模效能：** 解析 Markdown 引用改為逐文章線性掃描 + Map 查詢，避免 5,000 個 Markdown 與 50,000 個媒體物件互相做巢狀掃描。媒體改成增量後，整站 Astro HTML 建置本身的計算成本仍是另外的優化項目。
