# S3 圖床設定｜GitHub Secrets、Actions 填寫及成功驗收

本 CMS 使用單一 GitHub Actions 工作流程，支援 Backblaze B2、Cloudflare R2、AWS S3 等相容服務；**測試成功會自動更新 `site.config.json`，不是只有測試**。設定失敗不更改正式站的設定與已發布圖片網址。

## 第一步：儲存 S3 KEY（首次一次就好）

在**你自己的私人網站倉庫**中進入：

`Settings → Secrets and variables → Actions → Repository secrets → New repository secret`

兩組 Secret 都放在**下面的 Repository secrets**，不要放上面的 Environment secrets。

| Name（直接照抄） | Secret value（到 B2 取得） |
| --- | --- |
| `S3_ACCESS_KEY_ID` | Backblaze B2 的 Application Key ID |
| `S3_SECRET_ACCESS_KEY` | Backblaze B2 的 Application Key |

按兩次 `New repository secret` 分別儲存。儲存之後只會顯示 Secret 名稱，**看不到原本的值是正常的**，不需要多申請 GitHub Token。要換 KEY 才點 Secret 名稱更新值。

> B2 使用一般 Application Key，不用 Master Key。只給需要的 Bucket 操作權限即可；如有單桶授權而不能 ListBuckets，在下步手動填桶名就好。

## 第二步：在 Actions 選 B2 機房、填 CDN

開啟倉庫的 **Actions → 圖床設定｜S3 一站式驗證與套用 → Run workflow**。先確認 `Use workflow from: main`。

以 `holeboom.com` 原本使用的 B2 為例：

| GitHub Actions 欄位 | 怎麼填 |
| --- | --- |
| S3 供應商＋機房 `endpoint_preset` | 選 `b2-us-west-002` |
| S3 API Endpoint `endpoint` | 可直接填 `https://s3.us-west-002.backblazeb2.com`，或留空讓預設帶入；**這是 S3 API，不是圖片 CDN** |
| Bucket `bucket` | `wordpress-cdn`。留空才會嘗試列桶，有多個 Bucket 或無列桶權限時請填 |
| 自訂 CDN URL `cdn_url` | **第一優先**：有自訂 CDN 就填完整公開 HTTPS 前綴，例如 `https://cdn.example.com/file/wordpress-cdn/` |
| B2 原生公開網址開關 `b2_public_url` | **只有 `cdn_url` 留空、而且你要使用 B2 原生公開連結時**才手動選 `enabled`；預設 `disabled` |
| Cloudflare R2 Account ID `account_id` | B2 不填 |
| Region `region` | 選 B2 預設機房時不填；`custom` 才填 |
| Runner `runner` | 一般選 `github-hosted`，若 GitHub 額度不足才當次選 `self-hosted` |

**規則很簡單：自訂 CDN 優先，沒有自訂 CDN 才讓你手動開啟 B2 原生公開下載網址。** 沒填 CDN、也沒啟用 B2 原生公開連結就停下提示；不擅自改 Bucket 的公開／私有設定。

使用 B2 原生模式時，程式使用 B2 授權回應的 `downloadUrl` 得到正確下載主機，再組合 `/file/Bucket/`；不會猜 `f002`、`f003`，也不會自動把私人 Bucket 變成公有。真正私有 Bucket 若希望一般網站訪客看到圖片，請先配置能代理授權讀取的公開 CDN；只有授權用戶能看的附件不適用目前公開圖床設定。

## 第三步：按 Run workflow，檢查結果

1. 按綠色 **Run workflow**，回到工作流程列表，點進最新的執行紀錄。
2. 查看 **「找 Bucket，實測上傳與 HEAD 連結，通過才儲存設定」** Job。會先嘗試列桶（無此權限時驗證明確指定的桶），判斷 B2 的原生或自訂 CDN URL，再上傳**一個很小的固定測試檔**。
3. 對該公開 URL 送**一次 HTTP HEAD**，確認不是 HTTP 404、403；**不下載檔案、不做 SHA-256 比對，也不重複檢查所有圖片**。
4. 在 Actions 執行頁的 **Job summary／圖床連線實測結果** 看 Endpoint、Bucket、實際使用的 CDN 前綴、上傳與連結狀態。**畫面會印 URL 及檢查結果，不會印金鑰值。**
5. **S3 上傳、CDN HEAD 及既有媒體設定相容性檢查通過，就會只更新 `site.config.json` 並提交 `main`。** 此流程不執行整站 `npm run verify`，不重新產生內容報表，也不檢查文章、SEO、301 轉址。網站完整驗收由獨立的「網站自動驗收」Actions 負責，若網站內容有問題會在該流程另行報錯，不影響已完成的圖床設定提交。Cloudflare Pages 的網站建置／部署亦是獨立階段。

### 常見錯誤對照

| 錯誤 | 排查 |
| --- | --- |
| `S3_ACCESS_KEY_ID` 或 `S3_SECRET_ACCESS_KEY` 缺失 | 回 Secrets 看兩個名稱是否都在 **Repository secrets**，注意大小寫 |
| `AccessDenied`、`InvalidAccessKeyId` | 確認 B2 Key ID、Application Key、Bucket 授權；不要把 B2 Native 的 Bucket ID 當作桶名稱 |
| `NoSuchBucket` | Bucket 名稱與實際區域是否正確 |
| `AuthorizationHeaderMalformed`、`SignatureDoesNotMatch` | 端點與 Region 不一致；B2 `us-west-002` 對應 `https://s3.us-west-002.backblazeb2.com` |
| B2 原生 URL 不能取得 | 若 Key 權限受限或 B2 未回 downloadUrl，請填自訂 CDN URL；不會憑空推導網域 |
| S3 上傳成功但 CDN HEAD 404 | 檢查 CDN Origin／回源目錄／Bucket 公開讀取權限；**S3 Endpoint 不能直接當作 CDN** |
| CDN HEAD 403 | 公開網站圖片不能匿名存取；私桶要先有授權代理，系統不會幫你改為公開 |
| 仍是 Runner 啟動失敗、沒有任何 step | 這屬 GitHub Actions 額度或 Runner 問題，並非 S3 金鑰測試失敗；可下次 Run 時選 `self-hosted` |

### 遇到「圖床成功，但網站轉址錯誤」

圖床設定不再因文章 `aliases`、301、SEO 或 Sitemap 錯誤而回滾。如果先前的執行日誌顯示 **S3 上傳成功 + CDN HEAD 成功**，卻因網站結構報表中斷，那是舊版工作流程的問題；使用更新後的 `main` 重新執行即可。若後續網站自動驗收仍顯示重複轉址，請在網站驗收工作流程獨立修復，不必重複修改 S3 金鑰。

## 重要邊界

設定完成後，日常上傳只看 B2／S3 API 成功回應，再對**本次新圖片**做一次 HEAD 確認連結沒有死圖。普通 CI 不會下載圖片或執行每週巡檢。

S3 API Endpoint 是 `https://s3.us-west-002.backblazeb2.com`；你貼過的 `https://f002.backblazeb2.com/file/wordpress-cdn/...` 是**B2 公開下載網址**。這兩個網址用途不同，不能填反。

原有圖片及 Post/Page URL 不做遷移；變更已有媒體收據的 Bucket、來源或公開 CDN 路徑會受相容性檢查阻擋。

## 用已經存好的 KEY 上傳圖片、PDF 或 ZIP

設定成功後，到 **Actions → 媒體上傳｜圖片與 PDF／ZIP 附件 → Run workflow**，填內容 UID、HTTPS 檔案來源網址（或 Repo 內的 source_path），需要寫入 CPT 欄位則填 `field`。第一次保留 `dry_run: true` 預覽，確認後改為 false；系統會讀取這裡設定的 `S3_ACCESS_KEY_ID`／`S3_SECRET_ACCESS_KEY`，上傳後以單次 HEAD 檢查公開連結，並自動提交文章、媒體索引與結構報表到 main。**不必在 Actions 重填 KEY**。可選擇當次使用自架 Runner。完整欄位說明見 [圖片與附件操作](圖片操作.md)。
